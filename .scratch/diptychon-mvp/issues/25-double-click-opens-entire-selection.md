# 25 — Double-click opens the entire selection, not the clicked row

Status: ✅ done · bug — Option A implemented + user-verified 2026-06-30

## Parent

`.scratch/diptychon-mvp/PRD.md`

## Problem

With several rows selected in a Panel, double-clicking one row opens **all**
selected files rather than the row that was double-clicked. Reproduced after a
batch rename: select multiple files, ⌘R to rename them ("name 2", "name 3", …),
then double-click one of the still-selected rows — every selected file opens.

Likely path (needs confirming): the double-click action routes into
`WorkspaceModel.openSelection()` (`Sources/Diptychon/Panel/WorkspaceModel.swift:189`),
which loops over `activeModel.selectedItems` and opens each non-directory item.
So a double-click acts on the whole current selection instead of collapsing the
selection to the clicked row first (an unmodified click on a row should normally
reduce the selection to that single row before opening).

This is **pre-existing** — unrelated to the copy-overwrite fix or the
OperationCoordinator refresh refactor it was found alongside. No data risk.

## Decision (triage 2026-06-30): Option A

Double-click opens/navigates **only the clicked row**, sourced from the table's
clicked row — not the panel selection. `Return`/`↩` keeps "open the whole selection."

Rationale: Finder only *appears* to open-all — an unmodified click on a row in a
multi-selection collapses the selection to that row before the open fires, so just
the clicked row opens. Option A reproduces that effective behaviour and, by reading
the clicked row directly, is immune to the selection-collapse timing race the current
async `openSelection()` is prone to. (Option B was rejected: it keeps the timing
dependency.)

## What to build

- Stop routing double-click through `WorkspaceModel.openSelection()` (which loops over
  `activeModel.selectedItems`). Instead open/navigate the **clicked row** only.
- The clicked row is already known to `FileTableView` (`row(at:)` in `mouseDown`, and
  `NSTableView.clickedRow`). Prefer a table `doubleAction` / clicked-row path over the
  `WorkspaceView` NSEvent monitor's `clickCount == 2 { openSelection() }` so the open
  target is unambiguous and selection-independent.
- A folder row still **navigates into** the clicked folder; a file row opens in its
  default app — for the clicked row only.
- Leave `Return`/`↩` → `openSelection()` (open all selected) unchanged.

## Acceptance criteria

- [x] Intended behaviour decided and recorded here → **Option A** (clicked row only).
- [x] Double-clicking a row in a multi-selection opens/navigates **only** that row.
- [x] Single-click selection semantics on a row remain correct (reduces to one row).
- [x] Double-clicking a folder still navigates into it.

## Outcome (2026-06-30)

Fixed via the table's native `doubleAction` reading `clickedRow` (a new optional
`onActivate` on the list seam → `WorkspaceModel.activate(_:in:)`), replacing the
`WorkspaceView` mouse-monitor `clickCount == 2 → openSelection()` branch. Open target
is now the clicked row, independent of selection and of any collapse-timing race.
User-verified. 102 unit tests green (+ `ActivateTests`).

## Agent brief

> *This was generated by AI during triage.*

**Goal:** A double-click in a panel opens/navigates only the row under the cursor,
regardless of how many rows are selected. `Return`/`↩` is unchanged (opens the
selection).

**Root cause (confirmed):** Double-click is handled by the `WorkspaceView` local
`NSEvent` mouse monitor — on `event.clickCount == 2` it calls
`WorkspaceModel.openSelection()`, which loops over `activeModel.selectedItems` and
opens each non-directory item. The clicked row is never isolated, so a lingering
multi-selection (e.g. every row still selected after a batch rename) opens all of them.

**Fix approach:** Source the open from the **clicked row**, not the selection.
`FileTableView` already computes `row(at: downPoint)` in `mouseDown` and AppKit exposes
`NSTableView.clickedRow`. Prefer wiring a table `doubleAction` (or a clicked-row
callback through the existing list seam) that opens/navigates just that row, and remove
the `clickCount == 2 → openSelection()` branch from the `WorkspaceView` mouse monitor.
Reuse the single-item logic already in `openSelection()` (folder → `navigate(into:)`,
file → `NSWorkspace.shared.open`) but applied to the one clicked item.

**Key files:**
- `Sources/Diptychon/Panel/WorkspaceView.swift` — the mouse monitor's `clickCount == 2`
  branch (remove / repoint).
- `Sources/Diptychon/Panel/NSTableViewFileList.swift` — `FileTableView` (already has the
  clicked row; add the `doubleAction`/callback) and the `makeNSView` table setup
  (`table.target` is the coordinator).
- `Sources/Diptychon/Panel/WorkspaceModel.swift` — `openSelection()` stays for `Return`;
  add a single-item open path if cleaner (e.g. `open(_ item:)`).

**Watch out:** don't regress the slow-click inline-rename timing in
`FileTableView.mouseDown` (it cancels on double-click via `NSEvent.doubleClickInterval`).
The active panel must still switch on the click. Verify by manual run + ideally a UI test
(`DiptychonUITests`): select ≥2 rows, double-click one → only that one opens; double-click
a folder → navigates in; `Return` on a multi-selection → all open.
