## What to build

Cut the time a large folder takes to become interactive. Issue 22 measured the
baseline and it is **not** what "instant" implies: a 50k-file folder takes
**~4.6 s to load** (single panel) and **~6.5 s to fully interactive** (dual-panel
launch) on an M1 (Release, warm cache) — see `context/performance.md`. The load is
off-main so the UI never blocks, but ~92 µs/file is a real cost the user waits on.

Goal: materially reduce the per-file cost so a 50k folder loads in well under a
second, letting us make a *stronger* speed claim than "never blocks."

## Notes / design

- **Prime suspects** (`LocalDirectorySource.resourceKeys`, `LocalDirectorySource.swift`):
  two per-file resource keys prefetched for every row, both known-expensive:
  - **`contentTypeKey`** (UTType → the Kind column, issue 29).
  - **`localizedNameKey`** (Finder-style display name, e.g. "Musik" for Music).
- **Step 1 — confirm the cost before optimizing.** Don't guess: A/B the keys
  (load with/without each) via the `LoadPerformanceTests` fixture, or an
  Instruments Time Profiler run, to attribute the ~92 µs/file. Record which key
  dominates. (Issue 22 hypothesizes but did **not** measure per-key.)
- **Candidate fixes (pick after measuring):**
  - Derive `kind` lazily from the file extension (cheap string map) instead of a
    per-file UTType resolution; fall back to UTType only when the extension is
    unknown / when the row is actually shown.
  - Drop `localizedName` for non-system folders (it only differs for a handful of
    localized system dirs); use `name`/`lastPathComponent` otherwise.
  - Defer any residual per-file work to the ~visible rows (the table is already
    virtualized), computing the rest off-main after first paint.
- Keep the batched single `contentsOfDirectory(includingPropertiesForKeys:)` call —
  that part is already right (issue 01).

## Agent Brief

**Category:** enhancement
**Summary:** Cut per-file cost in the directory load path so a 50k-file folder becomes interactive in well under a second — measure per-key cost before optimizing.

**Current behavior:**
Loading a folder prefetches a set of `URLResourceKey`s for every entry in one batched `contentsOfDirectory(includingPropertiesForKeys:)` call (the batching is correct and stays). Baselines (issue 22, `context/performance.md`): ~4.6 s to load and ~6.5 s to fully interactive for 50k files on an M1 (Release, warm cache) — ~92 µs/file. Prime suspects are two prefetched keys: the content-type key (feeds the Kind column, issue 29) and the localized-name key (Finder display names).

**Desired behavior:**
Attribute the per-file cost by key (measure, don't guess), then reduce it so a 50k folder loads **< 1 s** single-panel. Keep the load off-main (UI never blocks) and keep the single batched enumeration call. Candidate fixes, chosen after measuring: derive `kind` lazily from the file extension via a cheap map, resolving `UTType` only for unknown extensions or actually-visible rows; skip the localized name for non-system folders (use `lastPathComponent`), reserving it for the handful of localized system dirs; defer residual per-file work to visible rows (the list is already virtualized).

**Key interfaces:**
- The directory source owning the `resourceKeys` prefetch set and the mapping from enumerated `URLResourceValues` to row models — its prefetch set and per-row derivation are what change. Displayed columns and sort behavior must stay identical.
- The Kind derivation feeding the Kind column (issue 29) — must still produce correct kinds; a lazy/extension-based path is fine as long as output matches.

**Acceptance criteria:**
- [ ] Per-key cost is measured (A/B with keys on/off, or Instruments Time Profiler) and the dominant key recorded in `context/performance.md`.
- [ ] 50k-folder single-panel load drops materially — target **< 1 s** on the issue-22 reference machine — and the new number is recorded.
- [ ] The load stays off-main; the UI never blocks during a large load.
- [ ] The Kind column and displayed names remain correct (localized system dirs still show their Finder name where that behavior is kept).
- [ ] `LoadPerformanceTests` and the wider suite stay green.

**Out of scope:**
- The virtualized list rendering (already O(visible)).
- Kind-column semantics (issue 29) beyond how the value is derived.
- Caching folder contents across navigations.
