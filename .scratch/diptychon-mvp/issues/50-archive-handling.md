## What to build (if the gate opens)

Smallest useful slice, in order of likely scope cut:

1. **Extract** — selected archive → extract into the current folder (or a
   same-named subfolder, Archive-Utility-style). Formats via what the system
   toolchain gives for free (zip/tar family); RAR/7z need a bundled lib —
   scope call for triage.
2. **Create** — selection → zip in the same folder. One format (zip), no
   options dialog.
3. **Browse archive as folder** (Nimble-Commander-style) — explicitly the
   heavy tier; likely out of scope for a first slice.

## Notes / design

- **Undo spine (#04):** extract → undo deletes the extracted output; create →
  undo deletes the archive. Both fit the existing command/undo model — no new
  undo semantics needed.
- **Implementation candidates** (triage picks): shell out to `/usr/bin/ditto`
  / bsdtar (zero dependencies, zip+tar family only) vs. bundling libarchive
  (more formats, size cost — watch the ~1.4 MB footprint claim on the /vs
  page; a fat archive lib could eat the wedge).
- **Positioning check:** the /vs axes today are native+size, keyboard,
  one-time, telemetry, persistence, undo — archive is *not* an axis Diptychon
  wins on. It closes a checklist hole, it doesn't sharpen the wedge. Another
  reason the gate must hold.

## Acceptance criteria (draft — firm up at triage)

- [ ] Extracting a .zip via keyboard command lands the contents in the target
      folder and is undoable.
- [ ] Creating a .zip from a multi-selection produces one archive and is
      undoable.
- [ ] Failures (corrupt archive, no space, name collision) surface through the
      existing operation-error path; never a half-extracted silent state.
- [ ] App size stays within the published footprint claim, or the /vs page is
      updated in the same change.
