# 53 — After Trash: move selection to the nearest surviving row (Finder parity)

## What to build

After trashing files (⌘⌫), the selection should land on the **nearest surviving
row** so the keyboard workflow *delete → keep navigating with arrow keys*
continues uninterrupted — exactly like Finder.

Today the deleted row vanishes on refresh and the selection becomes **empty**
(the selection is ID-based; a dead ID resolves to nothing). The table keeps
keyboard focus, but the next ↓ press restarts from row 1 (native `NSTableView`
behavior on empty selection) — the user loses their position in the list. Filed
from Till's question 2026-07-12 ("erlaubt mir nach dem Löschen einer Datei
weiter mit den Pfeiltasten zu navigieren?").

## Code analysis (verified 2026-07-12)

- `WorkspaceModel.trashSelection()` (`WorkspaceModel.swift:918`) only runs
  `TrashOperation` via the coordinator; `refreshBoth()` re-lists the panels.
  No reselect logic exists anywhere (`NSTableViewFileList.swift`,
  `PanelModel.swift` — no hits for nearest/reselect/survivor).
- Selection is deliberately **ID-based** (Marta-style, issue 28,
  `PanelModel.selection: Set<FileItem.ID>`) — robust against reloads, but it
  dissolves when the ID disappears. That design stays; this issue adds a
  one-shot reselect on top, it does **not** re-introduce index-based selection.
- ↑/↓ are native `NSTableView` navigation, not Keymap chords (only ⌘↑ is
  bound). Focus provably stays on the table — only the anchor row is lost.

## Notes / design

- **Finder's rule:** remember the *row index* of the first selected row before
  the operation; after the list updates, select the item now living at
  `min(rememberedIndex, count - 1)`. Multi-selection delete → use the smallest
  deleted index. Empty directory afterwards → empty selection, no crash.
- **Timing is the real work:** the trash is async (operation coordinator +
  refresh/`DirectoryWatcher`). The reselect must apply *after* the row set has
  actually changed, not synchronously in `trashSelection()`. A pending
  "reselect at index N" intent on the `PanelModel`, consumed by the next
  `visibleItems` update, fits the existing echo-guard pattern
  (`SelectionEchoGuard`, `NSTableViewFileList.swift:194`).
- Must hold in **filtered/search results** too: trashing a result while
  searching already triggers a refresh path (`PanelModel.swift:328`) — the
  reselect targets the nearest surviving *visible* row, not the raw directory.
- Trigger-agnostic: same behavior whether trash came from ⌘⌫ or a future
  context-menu item (it hooks the operation, not the key).
- **Out of scope:** ⌫ in the Staging pane (`removeFromStaging`) — different
  model (unstage, no disk delete); follow-up if the same annoyance shows up
  there. Also out: restoring selection after undo (put-back).

## Acceptance criteria

- [ ] ⌘⌫ on a single file → the row that took its place is selected; ↓/↑
      continue from there (verified live, per the real-call-path rule).
- [ ] Deleting the **last row** of the list → the new last row is selected.
- [ ] Multi-selection delete → selection lands at the smallest deleted index.
- [ ] Deleting the only remaining item → empty selection, no crash, no
      spurious highlight.
- [ ] Works identically in an active Filter/Search result list.
- [ ] Selection is a normal user selection afterwards (clears
      `highlightedTargetURL`, echoes to the table via the existing guard —
      cursor does not jump/scroll unexpectedly beyond revealing the row).
