## Problem

The reveal integration shipped with merge `24f9396` works and is verified:
with the `NSFileViewer` global default set to `com.diptychon.app`, "Show in
Finder" from browsers and other apps opens **Diptychon** and highlights the
file. But the only way to enable it is a Terminal command
(`defaults write -g NSFileViewer …`). A user who downloads the app from
diptychon.com will never do that — the feature exists, is our strongest
"replaces Finder in the daily loop" moment, and is effectively invisible.
ForkLift and Path Finder solve this with an in-app switch.

## What to build

A toggle in the app — Settings tab or first-run onboarding — labeled along the
lines of **"Use Diptychon when apps reveal files"**:

- **On** → write `NSFileViewer = com.diptychon.app` to the global defaults
  domain; **Off** → delete the key (restores Finder).
- Show the **current state truthfully** by reading the key, not by trusting a
  stored flag — the user can change it externally.
- Explain in one sentence what it does and what it does *not* do (see
  Non-goals), so expectations match Finder-parity reality.

## Code analysis (verified 2026-07-12)

- **Feasible without privileges:** app sandbox is OFF (ADR 0001,
  `Resources/Diptychon.entitlements`) — the app may write the
  `kCFPreferencesAnyApplication` (global) domain directly via
  `CFPreferencesSetValue` / `UserDefaults(suiteName: NSGlobalDomain)`.
  No helper, no admin prompt.
- **Settings window exists** (issue 44): `SettingsRootView`
  (`SettingsView.swift:31`) is a `TabView` with Shortcuts + Full Disk Access
  tabs. The FDA tab (`FullDiskAccessSettingsView`, `SettingsView.swift:154`)
  is the precedent for "system-level setup" UX — the new toggle is a third
  tab or lives with it on a "System Integration" tab.
- The receiving side already works and is merged: `public.folder` doc type
  (`Resources/Info.plist`) + `.onOpenURL` → `WorkspaceModel.openExternal`
  (`WorkspaceModel.swift`, merge `24f9396`).

## Notes / design

- **Open question (verify during build):** whether other apps pick up an
  `NSFileViewer` change immediately or only after they relaunch (each caller
  reads the global default through its own cfprefsd cache). Test with a live
  browser before wording the toggle's helper text; if a relaunch of the
  *calling* app is needed, say so in the UI.
- Placement decision (Till): Settings-only, or also a one-time onboarding
  prompt on first launch. Suggestion: Settings first — an onboarding prompt
  is a separate conversion experiment and shouldn't block this.
- Rollback safety: Off must delete the key (`defaults delete -g NSFileViewer`
  equivalent), never write `com.apple.finder` explicitly.

## Non-goals (proven dead ends — do not retry)

- **Default folder handler** (`open <folder>`, folder double-clicks →
  Diptychon): macOS 26 blocks this at the content-type level.
  `LSSetDefaultRoleHandlerForContentType("public.folder", …)` and
  `NSWorkspace.setDefaultApplication(toOpen: .folder)` both return
  `paramErr (-50)` **even with Finder itself as the target**, and the
  `LSHandlers` plist hack is discarded at login. Full evidence:
  `context/finder-replacement-runbook.md` ("Ergebnis").
- Desktop icons, Open/Save dialogs, Dock stacks — always Finder, out of reach.

## Acceptance criteria

- [ ] Toggle ON → "Show in Finder" from a real browser download opens
      Diptychon with the file highlighted (verified through the real call
      path, fresh app instances).
- [ ] Toggle OFF → same action opens Finder again; the `NSFileViewer` key is
      gone from the global domain (`defaults read -g NSFileViewer` errors).
- [ ] Toggle state survives app relaunch and reflects external changes
      (key set/removed via Terminal shows correctly after reopening Settings).
- [ ] Helper text states the scope honestly (reveal only — not folder
      double-click, not Desktop/dialogs).
- [ ] No admin prompt, no Terminal instructions anywhere in the flow.
