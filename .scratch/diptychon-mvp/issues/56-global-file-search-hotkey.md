## Problem

Spotlight und Raycast sind gut zum App-Öffnen, aber schwach für den Job
"finde eine Datei/einen Ordner und gib mir sie bzw. ihren Pfad ins
Clipboard". Till will aus jeder App heraus per Hotkey ein Such-Panel
öffnen, einen Treffer wählen und dann Pfad kopieren, Datei kopieren, in
Diptychon reveal'n oder mit der Standard-App öffnen — ohne erst zu
Diptychon zu wechseln.

## Entscheidungen (Triage-Session mit Till, 2026-07-12)

- **Hotkey-Scope: systemweit.** Diptychon läuft im Hintergrund, der Hotkey
  öffnet ein schwebendes Overlay-Panel (Spotlight-Stil) über der aktiven App.
- **Such-Scope: Spotlight-Index (mdfind/NSMetadataQuery).** Ganze indizierte
  Platte, sofortige Ergebnisse; die bestehende Fuzzy-Logik re-rankt die
  Index-Kandidaten. Kein eigenes Verzeichnis-Walking in diesem Issue.
- **Aktionen (alle vier), Default auf Return = Pfad kopieren:**
  1. Pfad kopieren (Return)
  2. Datei/Ordner kopieren — als File auf das Pasteboard, wie ⌘C im Finder
  3. In Diptychon öffnen/reveal — nutzt das bestehende Reveal-Routing
  4. Mit Standard-App öffnen

## Agent Brief

**Category:** enhancement
**Summary:** Systemweiter Hotkey öffnet ein nicht-aktivierendes Overlay-Panel
mit Spotlight-Index-basierter File-/Folder-Suche; Treffer bieten
Copy-Path (Return), Copy-File, Reveal-in-Diptychon und Open an.

**Current behavior:**
Diptychon hat eine In-App-Suche (Fuzzy-Matcher mit strukturellem
Score-Floor, Search=Home / Filter=aktueller Ordner) und ein
Keymap-System für In-App-Hotkeys über einen lokalen NSEvent-Monitor.
Beides ist unerreichbar, solange Diptychon nicht die fokussierte App ist.
Externe Reveals funktionieren bereits über das URL-basierte Reveal-Routing
(gemerged mit dem Finder-Replacement-Feature).

**Desired behavior:**
- Ein systemweiter Hotkey (Default **⌥Space**; als String in UserDefaults
  überschreibbar, kein Recorder-UI in v1) registriert sich beim App-Start
  über `RegisterEventHotKey` (Carbon) — bewusst diese API, weil sie ohne
  Accessibility-Permission funktioniert. Schlägt die Registrierung fehl
  (Kombination belegt, z.B. durch Raycast), erscheint einmalig ein Hinweis
  statt eines stillen Fehlers.
- Der Hotkey toggelt ein schwebendes, **nicht-aktivierendes** Panel
  (NSPanel, `.nonactivatingPanel`, Floating-Level, wird Key aber nicht Main),
  zentriert auf dem aktiven Screen: ein Suchfeld, darunter eine
  Ergebnisliste. Escape oder Fokusverlust schließt das Panel und gibt den
  Fokus an die vorherige App zurück.
- Tippen startet eine Query gegen den Spotlight-Index (Dateiname-Match,
  Files **und** Folders). Die vorhandene Fuzzy-Scoring-Logik re-rankt die
  Index-Kandidaten, damit das Ranking sich wie die In-App-Suche anfühlt.
  Ergebniszeile zeigt Name, Icon und den relativen Pfad (~-gekürzt).
- Aktionen auf dem selektierten Treffer:
  - **Return** → absoluten Pfad als Text ins Pasteboard, Panel schließt.
  - **⌘Return** (o.ä. konsistent mit Keymap-Konventionen) → Datei/Ordner
    als File-Objekt ins Pasteboard (Paste-fähig in Mail/Slack/Finder).
  - **Reveal in Diptychon** → Panel schließt, Diptychon aktiviert sich und
    navigiert über das bestehende Reveal-Routing zum Treffer.
  - **Open** → `NSWorkspace` öffnet den Treffer mit der Standard-App.
  - Alle vier Aktionen sind auch per Maus erreichbar (z.B. Action-Row oder
    Kontextmenü), Tastatur ist der primäre Weg.
- Nach einer Aktion oder Escape ist das Suchfeld beim nächsten Öffnen leer
  vorbelegt (kein Stale-Query-State).

**Key interfaces:**
- Der bestehende Fuzzy-Matcher (strukturierter Score mit Floor) — als
  Re-Ranker über die Index-Kandidaten wiederverwenden, nicht duplizieren.
- Das Keymap-/AppAction-System — die neuen Panel-internen Shortcuts sollen
  dessen Konventionen folgen; der **globale** Hotkey selbst läuft außerhalb
  davon (Carbon), das gehört dokumentiert.
- Das Reveal-Routing aus dem Finder-Replacement-Feature — die
  Reveal-Aktion ruft denselben Pfad auf wie externe Reveals, keine
  Parallel-Implementierung.
- Achtung Persistenz: keine Save-/Terminate-Observer in `@Observable`-Inits
  registrieren (bekannter Doppel-Init-Footgun, siehe #45).

**Acceptance criteria:**
- [ ] Bei laufendem Diptychon (auch ohne offene Fenster / im Hintergrund)
      öffnet ⌥Space das Such-Panel über der gerade aktiven App, ohne dass
      Diptychon die aktive App ersetzt (kein App-Switch in der Menüleiste).
- [ ] Eine Query wie `demand-test` findet `context/demand-test.md` unterhalb
      von Home; Ordner erscheinen ebenso als Treffer wie Dateien.
- [ ] Erste Ergebnisse erscheinen bei indizierten Volumes ohne spürbare
      Verzögerung (< ~300 ms nach Tippende, keine Walk-Latenz).
- [ ] Return kopiert den absoluten Pfad als Text; in ein Terminal einfügen
      ergibt den korrekten Pfad.
- [ ] Copy-File legt ein File-Objekt aufs Pasteboard; ⌘V im Finder erzeugt
      eine Kopie der Datei.
- [ ] Reveal-Aktion aktiviert Diptychon und selektiert/highlightet den
      Treffer über das bestehende Reveal-Routing.
- [ ] Open-Aktion öffnet den Treffer mit der Standard-App.
- [ ] Escape schließt das Panel und der Fokus liegt wieder auf der vorher
      aktiven App.
- [ ] Ist die Hotkey-Registrierung nicht möglich, gibt es genau einen
      sichtbaren Hinweis (kein Silent Fail, kein wiederholtes Nag).
- [ ] Volle Test-Suite grün vor Merge (nicht nur die Search-Suites).

**Out of scope:**
- Login-Item / "Start Diptychon beim Anmelden" (eigenes Issue, wenn das
  Feature sich bewährt).
- Hotkey-Recorder-UI in den Settings (v1: UserDefaults-String reicht).
- Inhaltssuche (Datei-Inhalte, kMDItemTextContent) — nur Namen/Pfade.
- Eigene Engine für unindizierte Volumes (Hybrid-Modus = mögliche v2).
- Änderungen an der bestehenden In-App-Suche oder deren Ranking.

**2026-07-12 — Raycast-Recherche (Frage von Till): Alternative/Vorstufe zu diesem Issue**

Drei Befunde, die die Build-Reihenfolge betreffen:

1. **Raycasts eingebaute File Search deckt den Kern-Job vermutlich schon ab:**
   Suche über Files & Folders mit Actions *Copy Name / Copy Path / Copy File*,
   Quick Look, Open in Terminal ([Manual](https://manual.raycast.com/file-search)).
   Vor jedem Build: eine Woche damit arbeiten. Wenn das reicht, schrumpft der
   Bedarf für dieses Issue auf die Diptychon-Integration.
2. **Eine eigene Raycast-Extension ist machbar und klein:** React/TypeScript/
   Node-22-API, lokal in Stunden gebaut, Store-Publishing optional via PR auf
   `raycast/extensions`. Die Diptychon-spezifische Action ("Reveal in
   Diptychon") braucht **kein URL-Scheme** — `open -a Diptychon <pfad>`
   triggert das bestehende Reveal-Routing (`bc15ba2`) schon heute.
   (Verifiziert: Info.plist hat kein CFBundleURLTypes; nicht nötig.)
3. **Store-Publishing als GTM-Kanal ist blockiert bis zur Notarisierung:**
   eine öffentliche Extension, deren Companion-App von Gatekeeper rejected
   wird, wäre ein schlechter erster Eindruck. Erst nach GO auf der Roadmap.

**Konsequenz:** Dieses Issue bleibt spezifiziert, aber die Reihenfolge-
Entscheidung (Raycast-Test → ggf. Extension → ggf. doch eigenes Panel) liegt
bei Till (PLAN.md › Offen — bei Till). Eine persönliche Raycast-Extension
wäre der billigere Demand-Test für denselben Job.
