# 49 — `diptychon://` URL scheme (open/reveal a path)

## What to build

Register a custom `diptychon://` URL scheme so any other app or script can tell
Diptychon to show a location — `open "diptychon://open?path=~/Downloads"` from
Terminal, a Raycast extension, an Alfred workflow, a Keyboard Maestro macro.
Diptychon ships one hook; the ecosystem builds the bridges. Safe, read-only
verbs only.

Two verbs:

- `diptychon://open?path=<folder>` — navigate the active pane to the folder.
- `diptychon://reveal?path=<file-or-folder>` — navigate to the parent and
  select/highlight the item (Finder's "reveal" semantics).

## Notes / design

- **Registration:** `CFBundleURLTypes` entry in the Info.plist. The project is
  XcodeGen-generated — declare it via `project.yml` / `Resources/Info.plist`,
  never the pbxproj.
- **Receiving:** the Finder-replacement work (uncommitted, see
  `context/finder-replacement-runbook.md`) already lands incoming open-events
  through SwiftUI `.onOpenURL` — URL-scheme opens arrive through the same entry
  point. Reuse that handler; branch on scheme vs. file URL.
- **Path handling:** percent-decode, expand `~`, resolve relative → reject
  (absolute or `~` paths only). Nonexistent path → no-op plus a non-blocking
  notice (same tone as the path-bar's failed "Go to Folder"). `open` on a file
  path → treat as `reveal` of that file (don't launch the file).
- **Navigation:** go through the existing navigate machinery (same path as
  issue 43's paste-a-path `navigateIfPath` / issue 15's Go to Folder), so
  history/back-forward and persistence behave identically to a user-driven jump.
- **Activation:** an incoming URL should bring the app forward (launch it if not
  running, activate the window if it is).
- **Security stance:** URL schemes are unauthenticated — any app can call them.
  Expose only navigation verbs. No delete/move/rename/execute verbs, ever, via
  this surface.

## Acceptance criteria

- [ ] `open "diptychon://open?path=~/Downloads"` in Terminal launches/activates
      Diptychon with the active pane showing `~/Downloads`.
- [ ] `diptychon://reveal?path=<file>` shows the parent folder with the file
      selected.
- [ ] Percent-encoded paths (spaces, umlauts) round-trip correctly.
- [ ] Nonexistent or malformed path → app activates, pane unchanged, notice
      shown; never a crash or a half-navigation.
- [ ] URL navigation shows up in back/forward history like any other jump.
- [ ] Works both when the app is already running and from cold launch.
- [ ] Finder-replacement odoc handling (plain file URLs) is unaffected.

## Out of scope

- Any mutating verbs (move/copy/delete/rename) — navigation only.
- A `search?query=` verb — plausible follow-up once local search (#43) semantics
  settle; don't build now.
- Shipping our own Raycast/Alfred extensions — the scheme is the enabler; first-
  party extensions are a separate GTM decision.
- x-callback-url response conventions (success/error callbacks to the caller).

## Open questions (for triage)

- Which pane does `open` target — always the active pane, or a `pane=left|right`
  parameter? (Active-pane-only is the simpler default.)
- Should `reveal` of an item inside a hidden folder force-show hidden files, or
  no-op with notice?
- Sequencing vs. the uncommitted Finder-replacement `.onOpenURL` work — this
  issue should land after that commits, to share one handler.
